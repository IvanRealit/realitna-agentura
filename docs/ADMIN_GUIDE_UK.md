# Робота персоналу

Вхід: `/admin`, лише власний обліковий запис. Створення початкового власника описано у README; пароль не зберігати в Git або документах. Немає публічної реєстрації. `npm run db:bootstrap` створює першого Super Admin без DEMO; seed вимагає APP_ENV=demo/test і додає DEMO-контент, не запускайте його на production як спосіб імпорту справжніх даних.

1. У Properties створіть DRAFT: slug, SK заголовок/опис, місто/регіон, ціну, характеристики і фото. Для першої публікації потрібні додатна ціна, фото та SK опис щонайменше 40 символів.
2. Agent заповнює власне оголошення й переводить у REVIEW. Manager/Admin перевіряє і переводить у PUBLISHED. Agent не публікує та не редагує вже опубліковане.
3. Якщо інший працівник змінив запис, сервер повертає VERSION_CONFLICT. Не перезаписуйте чужі зміни: збережіть свій текст окремо, перечитайте запис і узгодьте зміни. Видалення також потребує актуальної version.
4. Leads містить справжні збережені запити з сайту; змінюйте NEW/IN_PROGRESS/CLOSED, відповідального і нотатки відповідно до прав. Це ще не Client/Deal CRM.
5. Content редагує наявний контент/SEO; Settings — бренд/контакти/retention; Users — ролі та active; Audit — важливі зміни. Докладні права: `security/PERMISSION_MATRIX.md`.

На мобільному є нижня навігація dashboard/properties/leads; форми адаптуються до вузького екрана. Фізичний iPhone/камера/HEIC ще не перевірені. Немає безпечного offline cache персональних даних. Використовуйте вихід з облікового запису на спільних пристроях.

Немає екранів Finance, AML, Documents, Calendar або Backups; не вважайте їх прихованими готовими модулями. Не видаляйте дані для GDPR без перевірки правових строків і legal hold; чинний purge простий та потребує перегляду до production.

## Нове: філії та безпека

`/admin/branches`: створіть активну філію, потім призначте її працівнику в Users. Для Branch Manager/Coordinator філія обов'язкова; null branch не дає доступу до inventory. Manager legacy не обмежений філією. Archive відхиляється за наявності активних людей/об'єктів/open leads; спершу перепризначте їх.

`/admin/security`: змініть власний профіль, перевірте sessions/login history. Для TOTP адміністратор сервера має налаштувати MFA_ENCRYPTION_KEY. Введіть current password, перенесіть secret вручну в authenticator, підтвердьте актуальний код. Збережіть recovery codes у password manager: показуються лише один раз. Усі попередні sessions закриваються, увійдіть з новим кодом або recovery code. Повторний код не приймається.

Для запрошення створіть inactive користувача з унікальним випадковим стартовим паролем (не передавайте його), потім у Security виберіть INVITE. Передайте одноразовий token перевіреним захищеним каналом. Працівник відкриває `/account/activate` і вводить token/new password. Reset працює для active користувача, не вимикає MFA та завершує всі sessions після успіху. Токен не вставляти в URL, лист/чат сторонньому сервісу чи Git.

Зміна ролі/block/password/branch відкликає sessions і outstanding tokens. Для перенесення агента спершу перепризначте active property/leads. Бухгалтер поки має лише account security; Finance не реалізований. Auditor переглядає бізнес-дані без редагування.
